# Linux 7.2.7 전환 상태 — 2026-09-26

사용자가 지정한 커널 목표는 **7.2.7**입니다. 기존 Release 3의 실행 버전은
`7.2.7-linuxoss+`입니다. RHEL 8 사용자 공간을 유지하면서 Java/Tomcat과
Guardicore·Trend Micro의 보호 기능이 동작하는 것이 완료 기준입니다.

EL8 `.168` 호환 커널은 별도 비교 실험입니다. 그 커널에서의 모듈 적재 및
네트워크 시험 성공을 7.2.7의 호환성이나 취약점 조치 완료로 간주하지 않습니다.
`.168` 설치와 `stage-reviewed-modules.py` 실행은 7.2.7 전환의 선행 조건이 아닙니다.

## 현재 확인된 범위

- 7.2.7 Release 3 커널 RPM과 기존 부팅 시험 자료는 있습니다.
- 세 보안 모듈까지 함께 동작하는 7.2.7 호환 패치/RPM은 아직 없습니다.
- 실제 Guardicore 바이너리는 `proto`의 120/128 byte 위치를 sendmsg/recvmsg
  슬롯으로 사용합니다. 정확한 7.2.7 SDK에서 이 위치는 splice_eof/bind이며,
  sendmsg/recvmsg는 104/112 byte입니다. accept 콜백의 인자 형태도 바뀌었습니다.
  누락 함수 중계나 버전 문자열 변경만으로 해결할 수 없습니다.
- Trend Micro의 공식 Ubuntu 7.0용 필터·훅을 확보했습니다. 기존 4.18용보다
  가까운 포팅 입력이지만, 7.2.7에서 바로 사용할 수 있는 결과물은 아닙니다.
  GCC/DWARF 및 설정을 맞춘 컴파일 전용 비교에서도 구조체 차이가 남습니다.

추가 실험에서는 7.2.7을 실제 빌드·QEMU 부팅했습니다. Trend가 요구하던 누락
심볼은 0개가 됐지만 필터 36개, 훅 16개의 CRC 불일치와 `net_device` 직접 접근
위치 차이가 남았습니다. Guardicore는 27개 누락과 구조체 callback 차이가
유지됩니다. [상세 결과와 자체 호환 코드](../kernel-port7/README-ko.md)를 확인하세요.

분석 근거: [실제 서버 모듈 비교](../kernel-compat/SERVER-MODULES-20260926.md).
상용 모듈 원본과 디스어셈블리는 공개 저장소에 포함하지 않습니다.

## 남은 실제 작업

1. Trend 7.0용 바이너리가 사용하는 API, 할당 동작과 직접 필드 접근을 7.2.7에
   대조하고, 필요한 호환 구현을 보안 수정이 유지되는 형태로 작성·검증합니다.
2. Guardicore의 프로토콜 훅, 콜백 인자와 직접 구조체 접근을 함께 해결합니다.
   현 바이너리만으로 완성할 수 있는지는 아직 확인되지 않았습니다.
3. 수정된 7.2.7에서 세 모듈 적재·통신·해제, 에이전트 제어 및 실제 정책의
   허용/차단 동작을 검증합니다. 이어서 Java/Tomcat과 부팅·SSH를 검증합니다.
4. 최종 RPM에 맞춰 Trivy의 소스·수정 근거와 파일 해시를 갱신합니다.
   기존 Release 3에 고정된 CVE 판정을 새 바이너리에 그대로 적용하지 않습니다.

외부 모듈 설치 전 검사는 유지합니다. 아직 작성되지 않은 호환 패치나 수행하지
않은 운영 정책 시험을 완료로 표시하지 않습니다. 이 상태 정정에서는 운영
서버 설치·부팅 설정 변경·재부팅을 하지 않았습니다.
